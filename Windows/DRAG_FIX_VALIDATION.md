# Windowsドラッグ書き出し修正（1.0.4 / build 50）

## 実際の停止記録

2026-09-21 16:30:09 JST、1.0.1.48が.NET Runtimeのイベント1025でFailFast終了。
スタックは`HistoryList_PreviewMouseMove → DoDragDrop → OleDragOver → Invariant.FailFast`。
WPF 10.0.8の`OleDragOver`が保持データの非nullを要求する箇所に対応する。ASEファイル自体は生成済みで、ASE構造・保存済み履歴JSONの構文破損は見つからなかった。

複数の非同期書き出しからドラッグが重複開始される経路はコード上存在した。
ただし元の障害発生時のイベント全順序は記録されておらず、二重開始した瞬間の観測とは区別する。

## 修正

- 最初のawaitより前に操作を占有し、OLEのメッセージループから戻るまで占有を維持。
- 1回のマウス押下から開始できる操作は1回のみ。準備中の新しい押下は古い操作をキャンセル。
- 書き出し完了後、左ボタン、アクティブウィンドウ、モード、選択IDを再確認。
- ボタンを離す・Escape・非アクティブ化・モード変更・終了で準備をキャンセル。
- ドラッグ中の終了要求は操作終了を待ち、それから一時ファイルを破棄。
- 内部並べ替えの識別は、操作ごとの文字列トークンを用いる。別アプリのデータは並べ替えに使わない。
- Dropイベントは並べ替え先の記録だけとし、実際の履歴変更はDoDragDropが戻った後に行う。
- 並べ替えは開始時のIDを対象にする。途中で選択が変わっても別カードを移動しない。
- 書き出し一時フォルダを操作ごとに分離。拡張子や再ドラッグ時のファイル名を重複させない。

- xUnit 244件成功。新規10ケースは準備中100回の再入、OLE相当のネスト呼び出し、キャンセル、押し直し、失敗後の再操作、全3モードのID固定並べ替えを確認。
- 全3モードのオフスクリーン描画回帰テスト成功。バインディングエラー0。
- Win32 `IDataObject` / `CF_HDROP`で単体・複数ファイルを各50回受け渡し、日本語ファイル名と内部文字列トークンのCOM経由の復元を確認。クリップボードやユーザーのマウス操作は使用していない。
- WinSparkleは公式最新安定版0.9.4を再確認。完成品のDLLのバージョンとNuGetとのハッシュ一致を確認。
- 製品バージョン1.0.4、ファイルバージョン1.0.4.50。macOSのXcode設定は変更していない。

## 実マウス操作の検証境界

上記の自動テストとデータ転送テストは、Explorerへ実際にマウスでドラッグした確認ではない。
主担当のSSH実行はSession 0で、入力デスクトップ・カーソルにアクセスできないことを確認した。
Windows側のCodexへ独立検証を依頼し、`Windows/artifacts/drag-fix-codex-validation/`に実WPF/OLEの隔離試験プログラムを作成している。
元のFailFast再現・ゲートありとの比較・製品の実ドラッグ結果は、その実行結果を別途確認する必要がある。

この段階で、実ドラッグを含むすべての確認が完了したとは扱わない。
公開リリース、appcast変更、commit/pushは行っていない。

## 2026-09-21 標準リモート接続後の通常UI確認

Windows側のCodexへ、意図的な障害再現ではなくbuild 50の通常の選択・外部書き出しだけを依頼した。
既存5件の記録と設定を作業フォルダへ控え、履歴の削除・編集・並べ替え・新規測定・校正は行わない条件とした。

- 指定build 50のFileVersionとSHA-256は一致した。
- Computer Useの公開`launch_app`へ指定EXEの絶対パスを渡したが、実際にはインストール済み0.9.5.3が起動。実プロセスのパス・バージョンを確認し、履歴操作前に停止した。
- JavaScript文字列の二重バックスラッシュはなく、誤起動の根本原因は未確定。
- 誤起動した旧版だけを通常の「閉じる」で終了。保存確認は出なかった。旧インストールは変更していない。
- build 50の既存デスクトップショートカットのリンク先は正しい。
- Explorerでショートカットへ移動しようとしたが、上部が空白の画面となり、フォルダ移動・フォーカス変化を確認できなかった。画面取得と旧版の終了操作は成功したが、一般のクリック／キー入力の動作は確認できていない。
- WindowsはRDPのSession 1（Active）で動作し、WTSInfoExのSessionFlagsは1（Unlocked）。CodexとComputer UseヘルパーもSession 1に属する。ロックやSession 0上のGUI実行を原因とは断定できない。
- RDPの表示状態などを切り分けるため、ユーザーへ接続元画面を表示しているか確認を依頼した。レジストリ変更、権限変更、Explorer再起動、セッション切替は行っていない。

したがって、build 50はこのGUI確認では未起動で、実ドラッグ書き出しの合格判定はまだ出せない。
詳細と画像は`build/Windows-1.0.4-build50/product-ui-check-133b429b/`、Windows側では`Windows/artifacts/product-ui-check-build50-133b429b/`に保存している。
